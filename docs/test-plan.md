# Тест-план стенда embedded-qa-lab

Версія 2.0, 2026-11-02. Версія 1.0 охоплювала лише I2C-стенд у Wokwi, він тепер у розділі 6.1.

## 1. Мета

Перевірити, що інтерфейси Raspberry Pi 3 (живлення, GPIO, UART, SPI, I2C) і прошивка пристрою під тестом (Raspberry Pi Pico з дисплеєм) працюють відповідно до вимог, зокрема під навантаженням і при несправностях, а результати можна відтворити одним скриптом.

## 2. Обсяг

**Входить:**
- живлення плати: рівні 5 В і 3,3 В у простої та під навантаженням, прапорці `get_throttled`;
- GPIO: вихід, вхід з підтяжкою і без, PWM;
- UART: loopback на mini-UART і PL011, обмін з окремою платою (Pico), швидкості до 921600, тривалі прогони (soak);
- SPI: loopback, швидкості до 62,5 МГц;
- I2C: сканування шини, читання регістра ідентифікатора, негативні сценарії (у симуляторі);
- протокол прошивки Pico: луна, службові команди, обробка помилок вводу, зміна швидкості;
- вимоги R1–R4 до прошивки з дисплеєм (розділ 5).

**Не входить** (і чому):
- форма сигналів і таймінги на реальному залізі: немає логічного аналізатора й осцилографа, у симуляторі Wokwi трейси є;
- I2C з реальним датчиком: датчика немає (I2C-02 заблоковано);
- ЕМС, температурні камери, вібрація: немає обладнання;
- продуктивність Python-тестів понад межу ≈ 0,3 мс на повідомлення (обмеження інструменту, див. 8).

## 3. Стенд

| Що | Значення |
| --- | --- |
| Тестовий хост | Raspberry Pi 3 Model B Plus Rev 1.3, Raspberry Pi OS Lite 64-bit, ядро 6.18.50, Python 3.13.5, pytest 8.3.5 |
| Живлення хоста | окремий блок 5 В / 3 А (не USB-порт ПК, див. BUG-002) |
| DUT | Raspberry Pi Pico + TFT 1,54″ ST7789 (SPI), MicroPython, прошивка `src/pico/uart_echo_display.py`, `MODE = "fast"` |
| Живлення DUT | USB ПК (кабель з лініями даних), спільний GND з Pi 3 |
| Прилади | мультиметр ANENG SZ08 (DC V, межа 20 В), `vcgencmd`, `pinctrl`, лічильники драйвера `/proc/tty/driver/serial`, Shell Thonny |
| Симулятор | Wokwi: Pico + MPU6050 + логічний аналізатор, PulseView з декодером I²C |

Комутація:

| Фаза | З'єднання |
| --- | --- |
| loopback | пін 8 ↔ пін 10 (UART), пін 19 ↔ пін 21 (SPI), пін 11 ↔ пін 13 (GPIO17 ↔ GPIO27) |
| pico | перемичку 8 ↔ 10 знято; Pi пін 8 → Pico GP1 (пін 2), Pi пін 10 ← Pico GP0 (пін 1), Pi пін 6 — Pico пін 3 (GND) |

## 4. Підхід

| Рівень | Що робимо | Інструмент |
| --- | --- | --- |
| Електричний | замір напруги на пінах, порівняння з програмним станом | мультиметр, `pinctrl`, `vcgencmd` |
| Інтерфейсний | loopback: хост сам з собою, без DUT | `pytest`, `uart_speed_sweep.py`, `spi_speed_sweep.py` |
| Системний | хост ↔ DUT, протокол прошивки, негативні сценарії | `pytest` (`test_pico_uart.py`, `test_pico_display.py`) |
| Нефункціональний | soak (1000 повідомлень), прогін швидкостей, навантаження CPU, серія 30 прогонів для нестабільних тестів | ті самі скрипти, `yes > /dev/null` × 4 |

Принципи:
- Кожен результат має доказ: лог, скриншот або таблицю замірів з датою.
- Неочікуване значення спершу перемірюємо і перевіряємо методику (кабель, номер піна, контакт щупа), лише потім заводимо дефект. На стенді таких випадків було три, жоден не став хибним баг-репортом.
- Розбіжність з очікуванням, яку не пояснює методика, оформлюємо як баг-репорт за [шаблоном](bug-reports/TEMPLATE.md).
- Нестабільний тест (то passed, то failed) не перезапускаємо до «зеленого», а проганяємо серією і рахуємо частоту відмов.
- Для пошуку місця втрати даних використовуємо незалежні лічильники на обох кінцях лінії.

## 7. Регресійний прогін

Запуск з кореня репозиторію на Pi 3:

```bash
bash scripts/pi3/run_all_tests.sh loopback   # фаза 1: перемички, без Pico
bash scripts/pi3/run_all_tests.sh pico       # фаза 2: Pico з uart_echo_display.py (fast)
```

Скрипт фіксує коміт, версії, `get_throttled`, температуру, частоту ядра і лічильники UART до та після прогону, пише повний лог і JUnit XML у `logs/day3-<фаза>-<час>.*`.

| Фаза | Тестів | Результат | Час | `get_throttled` до / після | Лог |
| --- | --- | --- | --- | --- | --- |
| loopback | 4 | | | | |
| pico | 15 | | | | |

Коли запускати регресію: після кожної зміни прошивки DUT, оновлення ОС на хості, зміни `config.txt` (наприклад, `disable-bt`) і перекомутації стенда.

## 8. Ризики та обмеження

| Обмеження | Наслідок | Як пом'якшено |
| --- | --- | --- |
| Немає логічного аналізатора на реальному залізі | не видно форми сигналу, фактичної частоти SPI, таймінгів | місце втрати даних знаходимо лічильниками на обох кінцях (BUG-004); трейси I2C знято в Wokwi |
| SPI loopback не проводить SCLK через дріт | стійкість до 62,5 МГц не гарантує роботу реального пристрою на тому ж дроті | зафіксовано в SPI-03; потрібен тест з реальним SPI-пристроєм |
| Python-цикл «запит-відповідь» ≈ 0,3 мс на повідомлення | від 460800 бод тест вимірює швидкість скрипта, а не UART | для пропускної здатності потрібен потоковий тест |
| Pi 3 без радіатора, м'який ліміт 60 °C | таймінгові тести під навантаженням залежать від теплового стану | `get_throttled` і температура в кожному лозі; прогони під навантаженням починати після охолодження |
| Wokwi не моделює електрику | TC-08 не відтворюється, дребезг і струми не перевіряються | електричні кейси перенесено на Pi 3 |
| Pico живиться від ПК, прошивка запускається з Thonny | після перезапуску Pico прошивку треба запустити знову | перевірка `CMD:PING` перед фазою pico |

## 9. Критерії

**Вхід:** `get_throttled` = `0x0`, `/dev/serial0` вказує на очікуваний UART, комутація відповідає фазі, на Pico запущена потрібна прошивка (`CMD:STAT` показує `mode=fast`).

**Вихід:** усі автоматичні тести passed у двох фазах, логи збережено в репозиторії; кожен ❌ має баг-репорт; усі баг-репорти закрито або мають обґрунтоване рішення.

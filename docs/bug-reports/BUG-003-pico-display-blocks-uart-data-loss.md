# BUG-003: Pico з дисплеєм втрачає дані UART і спотворює наступну команду, поки малює на екрані

| Поле | Значення |
| --- | --- |
| Severity / Priority | Critical / High: тиха втрата даних (без жодної помилки на боці DUT) і спотворення наступної коректної команди |
| Виріб / плата, ревізія, серійний номер | Raspberry Pi Pico + TFT 1,54″ ST7789 240×240 (припаяний); хост Raspberry Pi 3 B+ Rev 1.3 |
| Версія прошивки (або хеш) | `src/pico/uart_echo_display.py`, `MODE = "legacy"` (логіка малювання зі старого проєкту `src/pico/legacy/main.py`), MicroPython |
| Відтворюваність | 3 з 3 вимог не виконано в одному прогоні; R1 — 4 з 5 повідомлень із затримкою |
| Дата | 2026-11-02 |

## Стенд

- Схема підключення: Pi 3 пін 8 (TXD) → Pico пін 2 (GP1 RX), Pi 3 пін 10 (RXD) ← Pico пін 1 (GP0 TX), GND пін 6 — GND пін 3. Дисплей: GP18 SCK, GP19 MOSI, GP12 RST, GP13 DC, GP14 CS. Деталі: [day4-pico-uart.md](../measurements/day4-pico-uart.md).
- Живлення: Pi 3 від блока 5 В / 3 А, Pico від USB ПК, між платами лише спільний GND.
- UART: 115200 8N1, на Pi `/dev/serial0 -> ttyS0` (mini-UART), на Pico `UART0`, `rxbuf=2048`.
- Прилади: `pytest` 8.3.5 на Pi 3 (`src/pi3/test_pico_display.py`), Shell Thonny на ПК.
- Температура / середовище: кімнатна.

## Кроки відтворення

1. Зібрати стенд за схемою вище.
2. У Thonny запустити `src/pico/uart_echo_display.py` з `MODE = "legacy"`.
3. На Pi 3: `pytest -v -s src/pi3/test_pico_display.py`.

## Очікуваний результат

- R1: луна на кожне повідомлення не пізніше ніж за 100 мс.
- R2: пачка 12 рядків × 200 байт (2400 байт) повертається повністю.
- R3: після навантаження `CMD:STAT` -> рядок, що починається з `STAT `.

## Фактичний результат

| Вимога | Результат |
| --- | --- |
| R1 | луна: 2,6 / 5539,4 / 5524,7 / 5530,9 / 5530,8 мс. Дані правильні, але з 2-го повідомлення затримка ≈ 5,5 с |
| R2 | `sent=12 received=10 ok=10 missing=['B10', 'B11'] time=97.4 s` |
| R3 | відповідь `b'B10-xxxx…xxxxCMD:STAT\n'`: початок обрізаного `B10` (80 байт) склеївся з командою, команду не виконано, у відповідь повернувся змішаний рядок |

## Аналіз причин

1. **Малювання блокує обробку UART.** Головний цикл синхронно викликає малювання після кожного рядка. Драйвер працює через `SoftSPI` на 200 кГц і малює текст по одному пікселю (на кожен піксель окремі команди `CASET`/`RASET`/`RAMWR`). Заміри з Shell Thonny:

   | Операція | Теорія | Факт |
   |---|---|---|
   | `fill(BLACK)`, 240 × 240 × 2 байти | 4,6 с (лише біти на дроті) | **5650 мс** (+23 % накладних витрат `SoftSPI` і MicroPython) |
   | малювання короткого рядка `lat-N` (`draw #1–5`) | | 5723–5789 мс (заливання + ≈ 80 мс тексту) |
   | малювання рядка пачки, 80 символів на екрані (`draw #6–16`) | | 6853–6886 мс (заливання + ≈ 1,2 с тексту) |

   Час R2 пояснюється повністю: ≈ 5,5 с DUT ще домальовував `lat-4` з попереднього тесту + 9 × 6,87 с до луни `B09` + 30 с тайм-ауту тиші на хості = 97,3 с (факт 97,4 с).
   Лічильник: 16 малювань = 5 (R1) + 10 (`B00`–`B09`) + 1 (склеєний `B10…CMD:STAT`, DUT сприйняв його як звичайний рядок і теж намалював).
2. **Переповнення буфера прийому без сигналу про помилку.** Поки DUT малює `B00`, хост досилає решту пачки за ≈ 0,2 с. Байти накопичуються в кільцевому буфері MicroPython (2048) і апаратному FIFO UART RP2040 (32), а все, що не влізло, мовчки відкидається. Перевірка: DUT прийняв 10 × 200 + 80 = **2080 байт = 2048 + 32**, втрачено 320 байт (хвіст `B10` разом із `\n` і весь `B11`).
3. **Немає ресинхронізації протоколу.** Обрізаний початок `B10` лишається в буфері DUT як недописаний рядок, і наступна повна команда дописується до нього. Тобто одна втрата даних ламає ще й наступну коректну команду. Ця вада не залежить від дисплея: так само спрацює будь-який загублений `\n` (шум, обрив дроту).

## Виправлення (режим `MODE = "fast"`)

1. Луна відправляється одразу, а дисплей оновлюється лише після `IDLE_MS` = 50 мс тиші на лінії і показує тільки останній рядок. Пріоритет у лінії, не в екрана.
2. Апаратний `SPI0` на 20 МГц замість `SoftSPI` на 200 кГц, текст рендериться в `framebuf` і передається одним записом смуги 240 × 40, а не по пікселю.
3. Ресинхронізація: недописаний рядок, після якого `LINE_TIMEOUT_MS` = 100 мс тиші, відкидається, лічильник `stale` у `CMD:STAT`. Перевіряє новий тест R4.

## Додатково

- Обхідний шлях без зміни прошивки: хост надсилає наступне повідомлення лише після луни і чекає ≥ 6 с (неприйнятно для реального обміну).
- Що вже перевірено: з тією самою лінією і без дисплея (`uart_echo.py`) 11 з 11 тестів пройшли, включно з 921600 бод, тож лінія і живлення ні до чого: причина в прошивці DUT.
- Урок: на DUT будь-яка довга синхронна операція (дисплей, запис у flash, датчик) в одному циклі з прийомом UART — ризик тихої втрати даних. Потрібні або переривання/DMA/окремий потік, або короткі неблокувальні кроки, плюс тайм-аут на недописаний кадр.
